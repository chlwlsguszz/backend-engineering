# 커머스 더미 데이터 구성

검색 결과에 나온 상품을 그대로 주문할 수 있도록 PostgreSQL의 `products`를 공통 카탈로그로 사용한다. 상품 한 행은 재고를 따로 관리하는 판매 단위(SKU)다. 예를 들어 한 운동화 모델에 색상 네 가지가 있으면 검색에는 상품 네 건이 잡히고, 주문은 선택한 색상의 재고만 차감한다. Elasticsearch도 같은 상품 ID로 색인한다.

## 생성 규모와 재현 조건

기본 개발 환경은 새 DB에 B9 상품 1,000개를 생성한다. 최종 부하 실험에 사용한 규모는 **상품 10,000,000개, 모델 2,500,000개, 회원 100,000명**이다. 분포를 먼저 검증한 파일럿은 상품 100,000개, 모델 25,000개, 회원 1,000명이다. 주문 건수는 생성한 상품의 수요와 가용 재고에 따라 결정된다. [B9 생성 SQL](../backend/src/main/resources/db/migration/B9__realistic_commerce_catalog.sql)

- `CATALOG_PRODUCT_COUNT`는 색상 옵션까지 포함한 SKU 수다. 기본값은 1,000이고 상한은 10,000,000이다. 파일럿은 100,000, 대용량 실험은 10,000,000을 명시한다. 회원은 SKU 100개당 한 명으로 올림해 생성하며 최소 50명이다.
- `CATALOG_SEED`의 기본값은 `42`다. 브랜드, 색상, 구매자처럼 추출할 속성마다 다른 키를 사용한다. PostgreSQL 16에서 생성기 버전과 입력값이 같으면 같은 카탈로그와 주문 이력을 재현할 수 있다.
- `CATALOG_AS_OF`의 기본값은 `2026-11-01T00:00:00Z`다. 출시와 주문 시각을 계산할 때 사용하는 기준점이다. 실제 사용한 값은 `catalog_seed_run`에 기록한다.

기존 V8 데이터베이스에는 B9가 소급 적용되지 않는다. 10만 건과 1,000만 건을 비교하려면 각 규모를 별도의 빈 데이터베이스에서 초기화한다. [파일럿 생성 절차](../readme.md#10만-건-파일럿-생성)

## 검색 데이터는 어떻게 구성했나

**모델과 색상 옵션.** SKU 32개를 모델 8개로 나누고 모델마다 1~7개 색상을 중복 없이 배정한다. 같은 모델의 옵션은 모델 코드, 브랜드, 품목, 가격, 출시 시각을 공유하고 색상과 재고는 개별 관리한다. 상품명에는 브랜드, 라인업, 성별, 품목, 모델 코드, 색상을 순서대로 넣는다. 그래서 모델 코드를 검색하면 같은 모델의 색상이 함께 나오고, 라인업을 검색하면 여러 모델이 나온다.

**브랜드와 필터 조합.** 브랜드 추출 가중치는 Nike 25%, Adidas 18%, New Balance 12%, 중간 규모 6개 브랜드 각 5%, 나머지 11개 브랜드 합계 15%다. 브랜드를 고른 뒤 카테고리를 정해 Nike에서는 신발, Patagonia에서는 아우터, Oakley에서는 안경 비중을 높인다. 색상도 카테고리와 라인업에 따라 가중치를 달리한다. 예를 들어 아우터의 기본 팔레트에는 검정과 네이비를, 트레일 라인에는 초록을 우선한다. 이 비율은 결과 건수가 다른 필터를 비교하기 위한 실험 가정이다.

**출시 시각.** 모델별 `created_at`을 기준 시각 이전 365일에 걸쳐 생성한다. 한정판과 트레일 라인은 약 90일 간격으로 배치한 네 개의 7일 구간에 출시가 몰린다. 같은 모델의 색상은 동시에 출시되므로 최신순 정렬에서 날짜가 다른 상품의 순서와, 날짜가 같을 때의 `id DESC` 순서를 모두 확인할 수 있다. `updated_at`에는 상품 변경 시각과 마지막 시드 주문 시각 중 더 늦은 값을 넣는다.

**10만 건 파일럿에서 확인한 분포.** 고유 상품명은 100,000개, 서로 다른 출시 시각은 25,000개였다. Nike 상품은 24,680개, Oakley 상품은 1,444개였다. 두 필터를 함께 적용하면 `TOP + BLACK`은 4,440개, `Oakley + GREEN`은 96개였다. 이 수치는 카탈로그에 들어 있는 상품 수다. 사용자가 각 조건을 얼마나 자주 검색할지는 부하 시나리오에서 별도로 정한다.

상품명에 해당 토큰이 들어 있는 **전체 SKU 수**를 기준으로, 기본 파일럿에는 다음 확인 사례를 두었다. 판매 상태 등 추가 필터를 적용하면 결과 수가 달라질 수 있다.

- `City000001`은 도시 컬렉션 128개, `Drop000001`은 한정 컬렉션 32개를 찾는다.
- `ME0000001`은 첫 모델의 색상 4개를 찾는다. `ME0000000`은 결과가 0개인 경우를 확인하는 코드다.
- `StudioCapsule`은 첫 13개 SKU에 붙인 단어다. 페이지 크기가 12이면 두 번째 페이지에 상품 하나가 남는다.

## 주문 이력과 재고는 어떻게 맞췄나

1. **공급을 먼저 정한다.** 일반 SKU의 기초 가용 재고는 0~80개, 한정판은 0~4개다. 일반 상품은 수요가 높을수록 추가 입고 확률이 올라가고, 한정판은 8% 확률로 1~3개가 입고된다. 단종 상품은 재고가 0이다. 입고는 기간 중 누적 수량으로 관리하며 개별 입고 시각은 생성하지 않는다.
2. **실제 상품과 회원을 연결한다.** 모델, 브랜드, 한정판 여부, 대표 색상 여부로 1~100점의 수요 점수를 만든다. 점수가 높을수록 구매 시도 확률과 가능한 반복 주문 수가 커진다. 인기순에 쓰는 `popularity_score`는 이 점수의 제곱이다. 실제 판매량은 `orders`에서 따로 집계할 수 있다.
3. **주문 가능한 수량만 배정한다.** 구매자는 생성된 회원 중에서 고르고 주문 시각은 상품 출시 이후로 정한다. SKU별 주문을 시간순으로 처리해 요청이 남은 재고를 넘으면 남은 수량만 배정한다. 재고가 0이면 해당 주문 행을 만들지 않는다. 주문 금액은 상품 단가에 실제 배정 수량을 곱한다.

시드 생성 직후에는 모든 SKU에서 아래 식이 성립해야 한다. `CREATED` 주문도 재고를 점유하고, `CANCELLED` 주문은 최종 재고에서 차감하는 수량이 0이다.

```text
현재 가용 재고 = 기초 가용 재고 + 누적 입고량 − CREATED 주문 수량 − CONFIRMED 주문 수량
```

첫 세 SKU는 정합성을 눈으로 확인할 수 있도록 값을 고정했다. **SKU 1**은 기초 120개에 10개를 입고하고 확정 주문 3개와 생성 상태 주문 7개를 차감해 **120개**가 남는다. 별도의 취소 주문 2개까지 빼면 잘못된 결과인 118개가 나온다. **SKU 2**는 `2 + 1 − 2 = 1`로 마지막 한 개가 남고, **SKU 3**은 `1 + 1 − 2 = 0`으로 품절된다.

주문 대상 1,000개가 필요할 때도 기존 카탈로그에서 `ACTIVE`이고 재고가 양수인 SKU를 최대 1,000개 고른다. 추출 결과에는 상품 ID, 추출 시점의 가용 재고, 단가가 들어간다. 이 과정에서 생성되는 파일은 기존 상품을 가리키는 목록이다. [주문 대상 추출 SQL](../scripts/sql/seed_order_products_1000.sql)

## 생성 결과 확인

상품을 수정하거나 새 주문을 넣기 전에 프로젝트 루트에서 아래 명령을 실행한다. 10만 건 파일럿을 검증할 때는 프로젝트 이름으로 `marketengine-catalog-pilot`을 사용한다.

```powershell
$env:COMPOSE_PROJECT_NAME = 'marketengine-catalog-10m'
.\scripts\sql\run-check-catalog-distribution.ps1
```

검증 SQL은 PostgreSQL의 같은 스냅샷에서 상품 분포와 검색어별 건수를 집계한다. 이어서 `catalog_seed_inventory`에 보관한 기초 재고와 입고량을 실제 주문 행에 대조하고, 날짜 순서, 주문 금액, 모델 내 색상 중복도 검사한다. 모든 검사를 통과하면 `Catalog seed checks passed.`가 출력된다. [분포 및 정합성 검증 SQL](../scripts/sql/check_catalog_distribution.sql)
