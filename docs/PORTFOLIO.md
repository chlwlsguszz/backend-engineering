# Market Engine | 1,000만 상품 검색과 주문 재고 정합성

마지막 재고 한 개를 주문한 직후 응답이 끊기면, 고객은 주문이 접수됐는지 모른 채 구매 버튼을 다시 누릅니다. 저는 이 상황에서 고객이 원래 주문을 확인하고, 재고는 정확히 한 번만 줄어드는 커머스 백엔드를 만들었습니다. 같은 상품을 검색하고 주문하는 과정을 1,000만 SKU 규모의 카탈로그로 확장하고, 검색 엔진 장애와 중복 요청을 직접 재현했습니다.

**개인 프로젝트에서 맡은 범위**는 카탈로그 생성, 검색 API와 색인, 주문 트랜잭션, 브라우저 재시도, 부하 검증입니다. Java 21과 Spring Boot로 API를 구현하고 PostgreSQL 16을 주문과 재고의 원본으로 사용했습니다. Elasticsearch 8.17은 검색을, Redis는 반복되는 목록 조회를 담당합니다. Next.js 화면과 k6로 서로 다른 실패 조건을 재현했습니다. [프로젝트 저장소](https://github.com/chlwlsguszz/backend-engineering)

## 검색과 주문이 같은 상품을 사용하도록

초기에는 주문 실험용 상품 1,000개를 따로 만들었습니다. 검색에서는 잘 노출되는 상품이 주문 경합 실험에는 등장하지 않았고, 실험용 상품을 추가하면 인기순 검색 결과까지 바뀌었습니다. 상품 생성 시각도 한 값에 몰려 최신순 정렬이 사실상 ID 순서로 결정됐습니다.

모델별 출시일을 1년에 걸쳐 배분하고 브랜드, 카테고리, 색상에 서로 다른 가중치를 적용했습니다. 한 모델에는 색상 옵션을 1~7개 두고, 옵션마다 하나의 SKU와 재고를 배정했습니다. 주문 실험은 이 카탈로그에서 판매 가능한 SKU를 읽어 대상을 정합니다. 같은 데이터에서 검정 상의는 440,490개, 특정 모델 코드 `ME0000001`은 4개가 검색 조건에 맞습니다. 결과가 많은 탐색과 모델을 지정한 탐색을 따로 실험할 수 있습니다. [카탈로그 설계](DUMMY_DATA_DESIGN.md)

**검증** — 10만 SKU에서 먼저 분포와 재고를 대조한 뒤 B9 카탈로그를 1,000만 SKU, 회원 10만 명, 초기 주문 126,373건으로 생성했습니다. 각 SKU에서 기초 재고와 입고량을 더하고 유효 주문 수량을 뺀 결과를 현재 재고와 비교했습니다. 불일치는 **0건**이었습니다. [전수 검증 기록](IMPROVEMENT_LOG.md#10만-sku-파일럿에서-보강한-생성-규칙)

## 마지막 재고에서 드러난 중복 주문

같은 주문 요청 두 건이 동시에 들어오면 둘 다 멱등성 키 조회를 통과할 수 있습니다. 첫 요청이 마지막 한 개를 구매하면 두 번째 요청은 주문을 INSERT하기도 전에 품절을 만납니다. 주문 테이블의 유니크 제약은 중복 저장을 막지만, 이미 성공한 고객에게 어떤 응답을 돌려줘야 하는지는 이 경로에서 결정되지 않았습니다.

브라우저는 한 번의 구매에 발급한 키를 새로고침 뒤에도 재사용합니다. 서버는 재고 부족이나 중복 키 충돌로 쓰기 트랜잭션이 롤백된 뒤 같은 회원과 키의 주문을 다시 조회합니다. 상품과 최초 요청 수량까지 일치하면 기존 주문 ID를 반환합니다. 신규 주문은 회원 조회, 조건부 재고 차감, 주문 저장을 한 트랜잭션에 묶었습니다. 차감에 성공한 SQL의 `RETURNING price_amount`로 구매 단가도 확정합니다. 주문을 수정하거나 취소할 때는 주문 행을 잠그고 점유 수량의 차이만 반영합니다. 이미 취소한 주문은 점유 수량이 0이므로 다시 취소해도 재고가 늘지 않습니다. [주문 생성 코드](../backend/src/main/java/com/marketengine/backend/order/application/OrderCreateExecutor.java) / [주문 변경과 재고 정책](ORDER_INVENTORY.md)

**검증** — PostgreSQL 16에서 동일한 입력으로 측정한 신규 주문당 HikariCP 커넥션 대여는 **3회에서 1회**로 줄었습니다. 실제 브라우저에서는 마지막 재고 주문의 성공 응답을 끊고 새로고침한 뒤 같은 주문 ID를 확인했습니다. 별도 1,000 SKU 환경의 k6 실험에서는 10초간 POST 60건을 보냈고, 중복 10건을 제외한 주문 50건과 재고 차감 50개가 일치했습니다. [커넥션 계측](IMPROVEMENT_LOG.md#멱등성-조회와-회원-조회를-주문-쓰기-트랜잭션으로-이동) / [k6 결과](K6_SCENARIOS.md#2026-11-10-실측-결과)

## 검색을 꺼도 주문이 남고, 복구하면 재고가 맞도록

초기 상품 변경은 DB 트랜잭션 안에서 ES 응답을 기다렸고, 주문으로 줄어든 재고는 검색 문서에 반영되지 않았습니다. 상품이나 재고가 바뀔 때 같은 DB 트랜잭션에 상품 ID와 변경 버전을 Outbox로 기록하도록 바꿨습니다. 별도 워커가 PostgreSQL의 최신 상태를 읽어 ES에 일괄 반영하고 실패한 항목을 재시도합니다. ES 문서에는 마지막 반영 버전과 삭제 표시를 남겨 늦게 도착한 변경이 삭제된 상품을 되살리는 경우도 막았습니다. 상품 상세와 주문 시점의 재고 판단은 PostgreSQL에서 처리합니다. [Outbox 설계와 구현](IMPROVEMENT_LOG.md#상품-변경의-검색-반영)

**장애 실험** — ES를 끈 상태에서 재고 10개인 상품을 2개 주문한 뒤 주문 수량을 3개로 바꾸고, 다른 상품 하나를 삭제했습니다. 대기 상품은 2개였습니다. ES를 켜자 검색 문서의 재고가 **7개**가 되고 다른 상품에는 삭제가 반영됐습니다. 같은 주문을 두 번 취소한 뒤에도 검색 재고는 **10개**, Outbox 대기는 **0건**이었습니다. [장애 재현 스크립트](../scripts/verify/run-commerce-smoke.ps1)

## 검색 성능을 측정한 두 가지 단위

**전체 색인 시간.** 순차 적재에서는 DB에서 5,000건을 읽은 뒤 ES 쓰기가 끝나야 다음 배치를 읽었습니다. 리더 하나가 상품 ID 순으로 읽고 여러 워커가 ES에 쓰도록 바꿨습니다. 대기 중이거나 실행 중인 배치를 최대 '워커 수 + 1'개로 제한해 ES가 밀리면 리더도 기다리게 했습니다. 기존 카탈로그의 첫 250만 건 저장 시간은 순차 338초, 워커 4개 130초였습니다. 실행 순서는 고정됐고 캐시 예열은 통제하지 않았습니다. 별도 V8 카탈로그에서 워커 8개, 배치 5,000개로 **1,000만 건 재색인에 5분 14.815초**가 걸렸고 저장 성공 건수와 최종 문서 수가 일치했습니다. 이 실행에서 마이그레이션을 포함한 Gradle 전체 시간은 8분 27초였습니다. [재색인 측정 기록](IMPROVEMENT_LOG.md#elasticsearch-재색인)

**검색 엔진에 도달한 쿼리 수.** 캐시가 있는 홈 피드에서는 높은 HTTP 처리량만으로 ES 부하를 알기 어렵습니다. 1,000 SKU, ES 단일 샤드에서 홈, 카테고리, 모델 코드, 깊은 페이지(`page=3`)를 각각 21회 요청했습니다. Redis를 켜면 앞의 세 조건은 각각 **ES 쿼리 1회**, 깊은 페이지는 **21회**였습니다. 캐시를 끄면 네 조건 모두 21회였습니다. 이 비교로 반복 조회에서 절약한 검색 호출과 깊은 탐색이 발생시키는 부하를 각각 확인했습니다. [캐시 비교 절차와 결과](K6_SCENARIOS.md#같은-피드로-캐시-효과-비교)

로컬 Docker 환경에서 백엔드 테스트 88개와 Chromium 브라우저 테스트 5개가 통과했습니다. 다음 성능 실험에서는 인기 상품에 중복 주문이 집중될 때 **다른 상품을 구매하는 고객의 p95와 커넥션 풀 대기**를 함께 추적하려고 합니다. 이 두 지표가 함께 증가하는 구간이 중복 요청용 락을 도입할지 판단할 기준입니다. [검증 현황과 후속 기준](PLAN.md)
